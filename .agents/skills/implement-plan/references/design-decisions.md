# Design decisions

Part of [spec-driven-dev](https://github.com/mkrtchian/spec-driven-dev/blob/main/README.md). The short version lives in the [README](https://github.com/mkrtchian/spec-driven-dev/blob/main/README.md#design-decisions). This page gives the detailed rationale behind each choice. Where published engineering work backs a choice, it is cited.

## A workflow, not an autonomous agent

The plugin is a fixed sequence of passes with human gates, not an agent that decides its own path. Anthropic's [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents) draws this line: workflows fit tasks with a predictable structure, autonomous agents fit open-ended tasks where the path can't be known in advance. Turning a discussed feature into reviewed code has a predictable structure: draft, review, check standards, run due diligence, break into steps, implement, check facts, verify. A fixed sequence makes each run predictable, debuggable, and cheap to reason about.

## Why not just plan mode?

Claude Code ships a native answer to "plan before you code": plan mode. It [separates exploration from execution](https://code.claude.com/docs/en/best-practices#explore-first-then-plan-then-code) inside one session. What it doesn't change: the plan lives in the conversation, and the context that wrote it is the context that implements it. This workflow adds what plan mode doesn't have. The plan becomes a durable file that goes through PR review. Dedicated agents review it without having seen the discussion. Implementation starts fresh, reading only the plan. Each step lands as its own commit. Checkpointing and `/rewind` cover undoing mistakes after the fact, review passes catch them before. Plan mode and the plugin complement each other: plan mode for quick scoped changes, `/small-change` when a change deserves a fresh review but not a plan, the full workflow when it deserves a reviewed plan.

## Isolated context per concern

Each review and implementation pass runs in a dedicated agent that has not seen the previous passes' context, only the artifacts they left behind. Drafting is the first of two deliberate exceptions: the orchestrator writes the plan itself, because the draft needs the discussion. `/small-change` is the second: the main session writes the code, for the same reason. Two reasons for the isolation, one about attention and one about bias.

**Attention.** A single long conversation degrades as context fills up. This is measured, not anecdotal: [Chroma's context rot report](https://research.trychroma.com/context-rot) shows performance dropping as input length grows, across 18 models, with task difficulty held constant. A review pass that carries the whole discussion, the draft, and its own tool history works under the conditions that report shows degrade performance, and Chroma expects the effect to be stronger on complex real-world tasks than on their controlled ones.

**Bias.** An agent that just spent 20 minutes implementing code is a poor judge of it. Claude Code's [best practices](https://code.claude.com/docs/en/best-practices#run-multiple-claude-sessions) state it directly: a fresh context improves review because the model "won't be biased toward code it just wrote", or in their one-line version, the agent doing the work isn't the one grading it.

Cognition reached the same conclusion in production with Devin, their coding agent: its review loop works best when "the coding and review agents do not share any context beforehand", and even on PRs written by Devin itself the clean-context reviewer catches an average of 2 bugs per PR ([Multi-agents working](https://cognition.ai/blog/multi-agents-working)). Their explanation is not the human defensiveness analogy (they note these agents "don't have egos"). It's informational: the clean reviewer is forced to reason backward from the artifact alone, so it questions things the author overlooked, and its short context keeps it sharp where the author's is already full.

Early empirical support points the same way: a [controlled preprint study](https://arxiv.org/abs/2603.12123) found fresh-context review beating both self-review (F1 28.6% vs 24.6%) and context-aware sub-agent review, with the benefit coming from the context separation itself. One small, single-model study, so treat it as a signal, not proof.

The effect has a broader base outside code review. Across 37 models and 9 benchmarks, [Lu et al.](https://arxiv.org/abs/2512.02304) find that a verifier's usefulness falls as its output distribution approaches the solver's: similarity raises the false positive rate and shrinks the measured gain, and their closing checklist recommends preferring verifiers that think differently from the solver. Reasoning post-training sharpens the effect instead of removing it, so a stronger model gains even less from checking itself. Their setting is single-answer verification rather than review of an artifact, so the mechanism carries over and the numbers do not. One axis of their ranking applies to this workflow, and Limits takes that up.

Isolation has a cost: a fresh agent inherits the project's `CLAUDE.md` files and the files they import, but none of the main session's conversation, so every pass re-derives from the artifacts what the discussion established. Nested `CLAUDE.md` files are the exception on the reading side: they load only when an agent reads a file in their directory, so each pass that touches a subdirectory pays that reading itself.

## A lightweight orchestrator

The orchestrator never loads the sub-agent prompts: the runtime resolves them through `subagent_type`. In the skill-based framework measured in the [March 2026 comparison](https://github.com/mkrtchian/spec-driven-dev/blob/main/docs/comparison.md), by contrast, the orchestrating agent loads the full text of each skill into its own context, and that text is resent to the model on every turn. Here each sub-agent reads the project context itself, explores the codebase, spends its own context doing it, and returns a short report (a status line like `STEP COMMITTED` plus findings). The orchestrator keeps the plan and those reports, nothing else. The rule is explicit where it matters most, and it enumerates what may cross: when an implementer reports a value it could not verify, the orchestrator carries the value, the file it landed in and the one-line reason into the fact-check prompt, and when the fact check reports a wrong value whose correction exceeds its write bound, it carries the true value, the source that settles it and the file the false value landed in into the relay implementer's prompt. Nothing else from either report enters its context.

The orchestrator is the longest-lived agent and the one you talk to, so its context is the most valuable to protect. Anthropic's [context engineering guidance](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) describes the same sub-agent pattern: the detailed work stays isolated in the sub-agent, the coordinator only sees condensed summaries. In `/small-change` the orchestrator is the main session, which writes the code itself, so the code enters its context and only the agents' prompt content stays out.

## A fresh start between planning and implementation

The discussion phase fills context with exploration, questions, dead ends, and design alternatives. By the time you run `/implement-plan`, you want an agent that reads only the plan: the same attention and bias arguments as above, applied between the two phases. This is also why the plan has to be self-contained: it's the only channel between the two commands. The separation is yours to enforce: you clear context (or open a fresh session) between `/write-plan` and `/implement-plan`, as the [README usage](https://github.com/mkrtchian/spec-driven-dev/blob/main/README.md#usage) shows.

## One writer at a time

The passes run in sequence, and each pass that decides an edit applies it itself. No pass hands a list of proposed edits to another agent to apply. Both halves of the rule are deliberate.

Three qualified exceptions, two of one shape and a narrower third of another. When the step hardener reports issues it can't fix, you choose between fix, skip, and stop, and on fix a fresh implementer receives the hardener's findings as prose while a new hardening pass verifies the result. When the fact check confirms a value wrong whose correction exceeds its write bound but for which the artifacts hold a single right answer, a fresh implementer applies it and a targeted fact-check pass re-verifies the corrected value against its live source before committing it. The shape is the same both times: a finding with one right answer is handed to the agent that can apply it, with a fresh verification pass behind it.

They are not authorized the same way. The hardener relay is human-authorized on every firing: it exists only as the fix branch of a choice you make. The fact-check relay fires without asking, on the orchestrator's own routing. That grant comes from the class it is bounded to. A finding qualifies only when the plan, the code and the source settle it, which is by construction the class that holds no decision anyone could be asked to make, so a gate there would return the same answer every time and spend the attention the single end-of-run interruption exists to save. The narrower third exception is not a relay at all. The orchestrator commits three things nobody else will write: the plan at the end of `/write-plan`, a step the hardener would not commit when you choose to skip it, and in `/small-change` the change it wrote itself. None of these applies another pass's findings, and all three stage by name.

**Sequential, not parallel.** Parallel writers make implicit decisions (style, interpretation of an ambiguity, edge-case handling) that conflict with each other. Cognition's [Don't build multi-agents](https://cognition.ai/blog/dont-build-multi-agents) names the principle: actions carry implicit decisions, and conflicting decisions carry bad results. Their production follow-up ten months later keeps the rule: multi-agent systems work best today when "writes stay single-threaded and the additional agents contribute intelligence rather than actions" ([Multi-agents working](https://cognition.ai/blog/multi-agents-working)). Anthropic's [multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system) adds the economics: parallel sub-agents pay off for breadth-first, read-only research (many independent questions fanned out at once), while coding offers fewer truly parallelizable subtasks. Sequential passes on verified state also keep failures local: when something breaks, one pass broke it.

**The pass that decides an edit applies it.** The dividing line is whether a finding has a single right answer that the artifacts hold. An import that does not resolve is one of those: whoever receives the report can check it against the plan and the code, so what the report left out is recoverable. A finding that rests on a judgment call has no such check. How a step should handle a partial failure is settled by a trade-off the files leave open, and judging it takes the context that produced it, which is what a report drops.

Anthropic calls the same hazard a game of telephone, and the remedy points to where the loss happens: sub-agents write their outputs to the filesystem for the next stage to read, instead of copying them through the coordinator's conversation history ([multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system), appendix). The loss comes from the relay, whatever it carries. What changes is whether the receiver can recover what was lost.

So a finding that rests on a judgment call stays with the agent that holds the context, or it comes to you. The hardener exception above takes the second path: what it could not fix reaches you first, and the relay happens only if you send it. Both relays keep a verification pass behind them, because the prose handover loses something whatever it carries. The fact-check relay is the cheaper of the two to justify, because it never hands over a judgment call at all: its class is defined by the artifacts holding a single right answer, which is the finding that survives the boundary, since the receiver can check it against the plan, the code and the source it was given. Each review pass here produces both kinds of findings at once, so it edits its artifact directly (the plan in `/write-plan`, the code in `/implement-plan`) and flags the rest, and apart from the two relays above, nothing sits between deciding an edit and applying it.

There's a second reason the orchestrator doesn't apply review findings itself: it wrote the plan. Filtering the review through the author reintroduces the bias that isolation exists to remove. Routing findings through it also adds to the context of the longest-lived agent in the run, a cost that stands whether or not fidelity is at stake.

The dividing line allows more than this workflow uses: several read-only reviewers can run at once, each classifying its own findings and handing the single-answer ones to one writer that applies them. The two relays above are that mechanism used one pass at a time. This workflow has no use for the parallel half, because its passes accumulate: each pass reads the artifact the previous ones have already amended, so it critiques the current state rather than the original, and none of them has to guess what the others will change. Running the reviewers at once gives that up, and reconciling findings that overlap is itself a judgment call, so here it would land in the orchestrator, which is both the context that has to stay small and the one that wrote the plan. The next section draws the same line at the last boundary: what a pass settles by itself, and what has to reach you.

## Fix what has one answer, flag the rest

Every review pass separates two kinds of findings. Corrections with a single right answer (a wrong file path, a type signature that doesn't match the code, a violation of a documented standard) are applied directly. Anything that needs a judgment call is flagged instead, as a `<!-- REVIEW: ... -->` marker in the plan or as a remark in the pass report, and routed to you.

Cognition calls the equivalent mechanism in Devin the "communication bridge": the filter that decides which review findings deserve action, using context the reviewer doesn't have ([Multi-agents working](https://cognition.ai/blog/multi-agents-working)). This plugin splits that filter in two. Mechanical fixes are the ones a reviewer can verify from the artifact alone, so they are safe to apply without the discussion context, and the plan gate plus per-step commits keep a misclassified fix visible and revertable. Judgment calls go to the person who has the discussion context. On the happy path you're interrupted once per command, at the end. Agents stop mid-run only on failures they can't resolve.

That placement is a bet, and Thoughtworks' [SPDD](https://martinfowler.com/articles/structured-prompt-driven/) bets the other way. It distributes intent confirmation across six checkpoints, on the argument that a single compressed review of the generated plan asks for more sustained attention than people actually give, so they "skim, defer, or approve by default". The bet here is that one checkpoint per command can be made light enough in the part that matters: what the passes settled is reported so you can audit it, and what they could not settle is separated out, so the block that needs your attention is the shortest one on screen. The plan gate also sits before any code is written. If runs show passes quietly overriding decisions taken during the discussion, the bet is wrong, and the fix is the mode Cognition runs in production, where the reviewer reports and the author applies, at the cost of the fidelity loss described above.

## External facts checked against live sources

The model's training cutoff mechanically stales third-party facts: library and CI action versions, API contracts, platform behavior, published identifiers and the values attached to them. A review that runs from memory cannot catch that staleness, because a stale fact looks exactly like a correct one. So the workflow checks facts against live sources in both of its phases, since a fact can enter the work at either one. Three agents can reach the web, and in `/small-change` so can the main session, under the same rule as the implementer (below). The same web-hygiene clauses bind all four.

`sdd-plan-diligence` runs at the end of `/write-plan`, after review and standards. Its fact-checking mandate is gated: a plan that cites and defers no external fact triggers no web call. The pass itself always runs, because its other mandates have an object on any plan: the risks you would implicitly approve by executing it, the `REVIEW:` markers earlier passes left behind, and the record it writes at the end.

`sdd-fact-checker` verifies the external facts the diff carries, after the last step in `/implement-plan` and after the change commit in `/small-change`. It exists because the plan pass cannot reach the case that matters most. A plan is allowed to defer a value to implementation (a column of published scores, an API field to be looked up when the code is written), and deferring is often the right call. The plan pass flags those deferrals and can settle one early by inlining the value, but a value it leaves deferred has no literal to check. That value becomes a literal for the first time during implementation, and every check that phase runs looks inward: tests, types, lint, and the diff-against-plan comparison all pass on a value that was invented, because the plan asked for a value and a value is there. Only a pass whose single question is "is this true" catches it. It is gated the same way, on the diff instead of the plan.

It runs first among the post-step passes, before standards enforcement and final review, rather than last. The last position in a run is the least-reviewed one by construction, since nothing reads the last pass's edits, and that is the wrong slot for the pass that ingests untrusted web content while holding write access to code. Running it first puts its own commit under both passes behind it. Neither re-checks a fact, so the ordering buys a second and third reader over the edit itself, while the truth of each fact still rests on the fact check alone. What it gives up is seeing their edits, which costs nothing here: the standards enforcer fixes naming and formatting, the final reviewer fixes typos, imports, dead code and obvious bugs, and neither introduces a version number, an endpoint, or an external identifier. It carries one mandate rather than the plan pass's four: the final reviewer already produces risks and trade-offs, and a diff carries no `REVIEW:` markers.

`sdd-implementer` reaches live sources through a single rule: when a step requires an external value it does not hold, it verifies rather than invents, and when it cannot verify, it may write a provisional value but must declare it in its report, naming the value, where it landed, and what would settle it. The orchestrator carries those declarations into the fact-check prompt. This widens the web surface to the agent that writes the most code, which is accepted for two reasons: it fetches only when it already knows a value is missing, and its diff is read by four fresh passes afterwards (the step hardener, then the fact check, the standards enforcer and the final review). A wrong value that never enters the code costs less than one corrected downstream. In `/small-change` the main session follows the same rule and lists its provisional values in the fact-check prompt, though three fresh passes read its diff instead of four.

An agent that ingests untrusted content, holds write access to code that will run, and can reach the network sits a notch above the same agent writing into a plan. Four constraints bound it: every correction is confined to the value itself, restructuring is forbidden (a wrong fact is fixed in place when the correction fits that bound, and otherwise reported: to a fresh implementer in `/implement-plan` when the artifacts still hold a single right answer, to you in `/small-change`, and to you in both when it takes a choice), a conclusion that crosses a context boundary is re-established rather than inherited (the implementer that applies a relayed correction never signs it off, a targeted re-check verifies the corrected value against its live source before anything is committed), and every correction lands in a commit that two later passes and then the human read.

All four web-reaching contexts route pages through `WebFetch` only, never `curl` or another raw fetch, and treat what comes back as data rather than instructions. The summarizing layer sits between the page and the agent's context, which narrows the surface for instructions smuggled into a page without closing it: a summarizer can still relay what it read. It does nothing against a page that is simply wrong. A source stating a false version or a false score passes any summarizer intact, since there is no injection to strip. That second failure mode is the one a fact pass exists for, and what covers it is the rest of the design: no pass takes another pass's conclusion as settled, every conclusion that crosses a boundary is re-established against its source by the pass that receives it, and every correction is visible in a commit the human reviews.

Both fact passes apply the review passes' fix-vs-flag split, this time to facts, two-way on the plan and three-way on the diff. A fact that is wrong or broken (a version, endpoint, or field that does not exist or is nonfunctional) has one right answer, so it is fixed in place, quoting old → new so the human can audit the edit. A fact that is merely valid-but-not-latest (a pinned `v4` when `v7` exists) is flagged, not changed: the pin may be deliberate, and only the human holds the discussion context to decide. A fact that cannot be verified is never guessed into a "verified" claim: it is reported open and handed to the human. The third branch belongs to the diff pass alone, and it takes a wrong fact whose correction exceeds what that pass may write: if the artifacts still hold a single right answer, `/implement-plan` sends it to a fresh implementer that applies it and a targeted re-check that verifies the result, and only a correction that takes a choice comes to you. `/small-change` has no relay, so there the single-answer correction comes to you as well. A relay would take a fresh implementer and a targeted re-check, two agents for a rare case on a small change. Having the main session apply the correction would still need the re-check, because only the re-check makes a relayed correction safe to commit. The plan pass gains nothing from that third route. Its bound is "never restructure the plan", and what it leaves unapplied is prose in a file you read and approve before any code exists, so an out-of-bound plan correction already has the human gate that the third route exists to supply on the diff, where the next thing that happens to an unapplied finding is a commit. The `<!-- REVIEW: ... -->` markers the plan pass collects reach the human before execution. The routing loop "Fix what has one answer, flag the rest" describes stops there: resolving them stays a human act that nothing downstream gates on.

## Dynamic discovery over configuration

The agents hardcode nothing about your stack. Each one discovers how the project works at run time: documented commands in `CLAUDE.md` first, then the project's own config files (`package.json` scripts, `Makefile` targets, `pyproject.toml`, `Cargo.toml`, `go.mod`, and equivalents) for tests, lint, and typecheck. Committing agents discover commit conventions the same way: `CLAUDE.md` rules first, then a `/commit` skill if the project has one, then commitlint or commitizen config. The alternative, a plugin config file mapping each project to its commands, would be one more artifact to write, keep in sync, and get stale. Reading the project beats configuring the plugin.

## Conditional TDD

Business logic gets test-first: the implementer writes the tests, runs them to confirm they fail, then implements until they pass. Glue code, wiring, and configuration get implemented directly, with tests after if they add value. The line is whether the step has behavior worth pinning down: a data transformation has expected inputs and outputs a failing test can capture, while a re-export or a config block has no behavior of its own. Such a step can still be tested, but the test only restates the line it covers, and it fails when that line is deleted or stops resolving. Applying test-first everywhere would produce ceremony tests that assert nothing. This is a prompt-level default with a stated exception, not an enforced gate (see Limits).

## Step hardening and the commit split

The implementer never commits. After each step, a fresh agent (the step hardener) reads the diff against the step and the plan, catches what emerged during implementation (broken imports, type mismatches, missed edge cases, shallow tests), fixes what has a clear answer, runs the project's verification commands, and only then commits. If it can't get verification to pass, it doesn't commit. It reports what failed, and the step stays open until you say how to proceed.

What protects the change is the sequence of passes, not the commit itself. Every step is read by an agent that did not write it, and the post-implementation passes read the whole diff again afterwards. Commits are how the run stays auditable: each step lands separately, gated on the project's verification commands (except a step you explicitly skip), so the branch you review shows what happened and in what order, including the fixes the later passes applied to their own findings. An intermediate commit records what happened. The sign-off is your review of the branch.

Splitting the work this way also keeps problems local to the step where they appeared, instead of surfacing at the end with five steps stacked on top. There is early quantitative support for this split: across 396 tasks and 23,392 episodes, [Khanal et al.](https://arxiv.org/abs/2603.29231) measure agent reliability falling as task duration grows, steepest on software engineering tasks, and argue that splitting a long task into segments and restarting the agent at each boundary is the most effective reliability intervention available to a harness. The size of the effect is softer than those numbers suggest. The decomposition figures are an extrapolation from the decay curve, since the study never ran an actual decomposition, and its open-weight models may sit at a different point on that curve than the models this plugin uses. The direction is what transfers here.

## Plans in git, no hidden state

The plan is an ordinary markdown file, committed to your repository, reviewed like any other change. No state directory, no database, no memory shared between agents outside artifacts you can read. Everything the workflow will do is inspectable before it runs, and everything it did is in git history after. To make the "committed to your repository" property real rather than a suggestion, `/write-plan` ends by proposing to commit the plan (staging only the plan file, never automatically): the workflow itself produces the committed artifact instead of leaving it to the user to remember.

This also supports the supervision posture [Kief Morris describes](https://martinfowler.com/articles/exploring-gen-ai/humans-and-agents.html) for agentic delivery. When the output is wrong you can fix the plan directly, which Morris calls working "in the loop". Or you can fix the prompts and process that produced it, working "on the loop", where the correction improves every future run. Because plans and prompts are both plain files in git, that second option stays cheap. Per-step commits give recoverable checkpoints, the same discipline Anthropic found necessary for [long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents): incremental progress, descriptive commits, a clean state after every session.

The plan is a record of intent for one change, not a living specification of the system. Nothing syncs it back afterwards: once the change lands, the plan stays what it was when you approved it, and it joins the commits as a fixed record of the work at a different level of detail. If your team already writes ADRs, the plan sits below them: the ADR for the architectural call, the plan for the change, the commits for the code. Other designs take the opposite branch. [SPDD](https://martinfowler.com/articles/structured-prompt-driven/) keeps its spec current in both directions, one command flowing requirement changes into the spec before the code and another flowing refactorings back, so the spec stays "an accurate record of the current system rather than a historical snapshot", what [Böckeler's taxonomy](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html) calls spec-anchored. That buys a durable artifact at the price of a second thing to keep true. This workflow stays spec-first, where most of the category sits.

One section of the plan is written by an agent for another agent to read, which sits close to the no-hidden-state line. `sdd-plan-diligence` ends by writing a `## Due diligence record` into the plan: one line per external fact the plan cites or defers, marked settled or open. That is not state the workflow keeps in sync. It is inspectable markdown, reviewed in the PR like the rest of the plan, written once and never refreshed, and nothing downstream is gated on it: `sdd-fact-checker` verifies every external fact in the diff whether the record calls it settled or not. Delete the whole section and the same facts still get checked, the pass just loses the plan-time context it prioritizes and reports with.

That refusal to let a line in the record buy a skipped check is deliberate, and it rests on an asymmetry between the two ways such a report can be wrong. A report that can only add work fails by costing time, and a needless check is cheap. A report that could remove work fails by costing coverage, silently, because a check that did not happen leaves no trace in any output. Under that restriction the record still closes a real gap: before it, a currency note or a fact diligence could not settle reached the human once in chat and then died at the `/clear` the workflow tells you to run between the two commands, so no implementation-phase pass knew which fact the plan phase was already unsure about.

## Small changes without a plan

In `/small-change` the main session writes the code, for the same reason the orchestrator drafts the plan itself: the change needs the discussion, and on a change this small, a plan able to carry that discussion to a fresh implementer would cost more than the change. That gives up one of the two benefits of isolation. The bias argument is about judging, so it still holds: every pass that judges the code starts fresh. The attention argument is given up: the code is written in a context that already carries the discussion, which is the cost the fresh start between planning and implementation exists to avoid. It is accepted here because the change is small.

Three to five lines of intent take the plan's place: the need, what counts as done, and the files the change should touch. The main session writes them before any code and commits them in the body of the change commit. The final review checks the diff against them, both what the diff misses and what it changes beyond them, and the fact check reads them where it would read the plan. The standards pass receives only the changed files, as in `/implement-plan`. Nothing approves the intent during the run: it heads the summary at the end, where you can catch a wrong one.

The main session also commits its own change, which the implementer never does in `/implement-plan`, and no hardener reads it first. With a single change there is no later step for a problem to be stacked under, and as in [step hardening](#step-hardening-and-the-commit-split), the change is protected by the passes that read it afterwards.

The fact check runs on every change rather than only when the main session thinks the diff carries an external value, because the context that wrote a value from memory is the one least able to tell it is stale.

The review passes still apply their own fixes. The alternative, where the reviewer reports and the author applies, has a stronger case here than in `/implement-plan`: the main session is the only context that holds the discussion, and there is no plan gate. It is still set aside, because the main session would filter the review of its own code. Across four coding and tool-use datasets, [Khullar et al.](https://arxiv.org/abs/2603.04582) find that a model reports risky or incorrect actions less often when the action appears in one of the model's own earlier turns than when the same action is shown to it in a new context. Their prompts are one or two turns long, so the main session here, which carries the whole discussion, is a case they did not test. Letting the passes apply their fixes is therefore a bigger bet than in the full workflow, though most of the risk sits in one pass. The fact check only changes a value a live source settles, and the standards pass only what a project document states, so the final review is the one pass whose fix can override a decision taken in the discussion. Its rule is written for that case: it fixes what the code and the intent settle, including an obvious defect like a crash or an injection, and flags a correction that depends on a choice the intent doesn't record, naming the decision that would justify the code as it stands. Each pass's fixes also land in their own commit and the summary lists them, so the fixes of a pass you disagree with are one revert away.

Which changes are small is left to the project, since whether a change needs a plan depends more on what it touches than on its size, and the project knows its own code where the plugin does not.

## Security on the diff

The due diligence pass flags the security decisions a plan takes on, but `/small-change` has no such pass. A flaw introduced while writing the code, like a query built by string concatenation or a credential pasted into the source, shows up only in the diff, so the check lives in the final review, which reads the full diff at the end of both `/implement-plan` and `/small-change`.

It is a conditional check inside that pass rather than a pass of its own. The fact check has its own pass because it needs what no other pass holds, live sources and the web-hygiene bounds that come with them. A security read of the diff starts from what the final review already reads: the full diff, the modified files in full, and the plan or the intent. The plan also keeps it from re-flagging a risk the plan records as accepted. It applies when the diff touches authentication or authorization code, a secret, a dependency, or outside data reaching a query, a shell command, a file path, a template or a deserializer.

It fixes only the patterns that have a canonical correction: a string-built query or command turned into the parametrized or argument-array form the codebase already uses, an unsafe deserialization call replaced by its safe counterpart. Everything else is flagged, input validation included, since whether an input needs validating is a choice. A secret found in the diff is flagged as blocking your push, listed first among the security findings, though nothing in the run itself stops on it. It is already in the local history, which a later commit that removes it would not clean, so the flag says to rewrite history before pushing and to rotate the secret. For a diff that deserves a full security review, run Claude Code's built-in `/security-review` from a fresh session, for the same reason the review passes start fresh.

## Limits

TDD, standards checks, and verification runs are instructions that models follow reliably in practice, not gates that stop a run. For stronger guarantees on tests, lint, and typecheck, pair the workflow with pre-commit hooks: they run on every commit, and every commit path in the workflow is instructed never to bypass them with `--no-verify`, so the pairing is not defeated in-prompt.

The web-hygiene clauses are instructions in the same way: nothing in the agent definitions restricts the tools an agent can reach, and the implementer and the fact checker need a shell to run verification commands. All of this also assumes your project exposes commands the agents can discover. Where discovery comes back empty, the passes still run and nothing gates them, which is where the pre-commit hooks become the only enforcement left.

Isolation here is contextual: every agent pass runs the same pinned model, only the context differs. The verification work cited above spans two distinct axes, the context a verifier carries and the distribution it samples from, and this workflow moves the first while leaving the second where it is. Lu et al. rank three settings by measured gain: a verifier from a different model family first, a different model of the same family second, the model checking itself last. On that axis the workflow sits at the bottom, and from isolation it can claim only the context effect.

A plugin cannot reach a different model family at all, since the `model` field selects within a single vendor's family, but it could run its review passes on a different model of the same family. This one does not yet: whether cross-model review pays for its added cost and latency is the kind of question the March 2026 benchmark is too small to answer. The workflow therefore claims less than independent verification. It changes the context a reviewer works from and leaves the model fixed, which is what the review evidence above measures: Chroma, Devin's review loop, and the fresh-context study all vary the context and hold the model constant.

Isolation is paid in wall-clock time and tokens. On the benchmark feature, the full workflow took ~22 min against ~15 min for frameworks without isolated review passes, with 6 agent invocations for a 2-step plan (see the [framework comparison](https://github.com/mkrtchian/spec-driven-dev/blob/main/docs/comparison.md), a March 2026 snapshot). The claim is quality and reviewability, not speed: net time saved against plain AI-assisted coding is unmeasured.

The full workflow is sized for multi-file features, and on a single-file fix or a small refactor its overhead exceeds the benefit. One fixed workflow can't fit every size of change, as [Birgitta Böckeler's analysis](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html) of spec-driven tools points out, so the plugin has a second command for small changes and leaves the line between the two to each project.

The machinery optimizes conformance to the plan, not the plan itself. If implementation reveals the plan's approach is wrong, agents flag what they can't fix and stop. Rewriting the plan stays your decision ([workflow.md](workflow.md) covers the failure paths).
