# Migrating a machine to the `mise dot` overlay layout

This is the procedure for a machine whose dotfiles repo is still checked out at `$HOME` and which needs to move to the layout `home-overlay` introduces: the repo lives at `~/dev/dotfiles`, and `mise dot` deploys its tracked files into `$HOME` as symlinks.

The repo has to be at `$HOME` before this runs (the old layout) and at `~/dev/dotfiles` after it.

## What changes on the machine

| Before | After |
| --- | --- |
| Repo root is `$HOME` | Repo root is `~/dev/dotfiles` |
| `$HOME/.git` is a directory | `$HOME/.git` is a plain directory of symlinks (no git repo) |
| Tracked files are real files in `$HOME` | Tracked files are symlinks into `~/dev/dotfiles` |
| Repo-only paths (`docs/`, `tests/`, `crates/`, `.github/`, `justfile`, `hk.pkl`, …) sit in `$HOME` | They live only in `~/dev/dotfiles` |
| Worktrees under `~/.worktrees/dotfiles/<branch>` | Worktrees under `~/.worktrees/dev-dotfiles/<branch>` |
| `wt` needs `--allow-home` | `wt` needs no flag (the repo is not `$HOME` any more) |
| `~/.config/wt/overlay/dotfiles` | `~/.config/wt/overlay/dev-dotfiles` |

The deploy spec is `.config/mise/conf.d/dotfiles.toml`, generated by `scripts/home_spec.py` from `git ls-files`. It has one explicit entry per tracked file (2299 `symlink` + 5 `copy` at the time of writing) because `symlink-each` into `~` walks the whole home directory and does not finish.

## Prerequisites

- `mise` installed and on `PATH` (`mise --version`).
- `git` 2.54+ (the repo uses config-based hooks, `hook.<name>.command`).
- A clean working tree in `$HOME` (`git -C ~ status --porcelain` empty).
- The `home-overlay` branch fetched (`git fetch origin home-overlay`).

## Phase 0 — Decide the branch to migrate

`home-overlay` and this machine's `weekend` branch have diverged and conflict in 18 files. `home-overlay` is already pushed; `weekend` may not be. Re-derive the branch state before merging:

```bash
git log --oneline origin/weekend..weekend     # commits on weekend that are not pushed
git cherry origin/home-overlay weekend        # "+" lines: commits not on home-overlay
```

Most conflicts are in generated files and are resolved by regenerating; two are semantic and need a decision. Merge `home-overlay` into `weekend` (so the unpushed work is kept and `home-overlay` is the incoming side):

```bash
git fetch origin home-overlay
git merge origin/home-overlay
```

Conflicts to expect, and how to resolve each:

| File | Resolution |
| --- | --- |
| `docs/harness/*.md`, `docs/harness/*.json`, `docs/harness/drift.jsonl`, `docs/agent-harnesses.{json,md}` | Generated. Take either side, then run `just harness-generate` to rewrite them. |
| `.omp/agent/config.yml` | Not generated — a live OMP config, and the conflict is semantic. `weekend` sets `memory.backend: mnemopi` and `home-overlay` sets `memory.backend: "off"`; `weekend` also carries an explanatory comment above the `disabledExtensions` entry that `home-overlay` drops. Take the setting you want and re-attach the comment. |
| `.config/mise/config.toml` | Tool pins. Keep the newer pins from `weekend`, but keep `github:phatblat/wt = "1.0.1"` from `home-overlay` — `wt` is only pinned there. |
| `.config/ness/policy.toml` | Not generated — a hand-written safety policy, and the conflict is semantic. `home-overlay` un-comments `bash`, `python` and `python3` in `no_session_approval` (so they are approved per exact command line, never per name), while `weekend` comments them out (so they are asked about every time). Pick one deliberately and re-run `just ness-policy-check`; the comments in the file explain the trade-off. |
| `.agents/skills/graphify/.graphify_version` | A version marker written by the graphify tool; the newer value wins. |

After resolving, regenerate and verify:

```bash
just generate
just check
git push -u origin <branch>
```

Do not migrate until this is merged and pushed: the deploy spec must exist on the branch you are going to check out, or `mise dot apply` has nothing to deploy.

## Phase 1 — Move the repo out of `$HOME`

This is the delicate step. `$HOME` currently *is* the work tree, so the work tree contents and `.git` have to be moved together, preserving every tracked path's relative position.

```bash
# 1. Work in a clean state.
cd ~
git status --porcelain          # must be empty

# Build the tar AFTER the merge is in place: it lists the working tree's
# tracked paths, so a tar taken before the merge omits every file the merge
# added. Building it later and extracting over the checkout is what fills
# those in.

# 2. Move the work tree contents into the new location.
mkdir -p ~/dev/dotfiles
# Move every tracked path, preserving structure, into ~/dev/dotfiles.
# Use git's own list so nothing is missed and nothing untracked is carried over:
git ls-files -z | tar --null -T - -cf /tmp/dotfiles-tracked.tar
tar -xf /tmp/dotfiles-tracked.tar -C ~/dev/dotfiles

# 3. Move .git into the new location and repoint the work tree.
mv ~/.git ~/dev/dotfiles/.git
```

`~/dev/dotfiles/.git` now describes a work tree rooted at `~/dev/dotfiles`, and `~/dev/dotfiles` holds the tracked content at the same relative paths. Verify:

```bash
git -C ~/dev/dotfiles rev-parse --show-toplevel   # -> /Users/<you>/dev/dotfiles
git -C ~/dev/dotfiles status --porcelain          # -> empty
git -C ~/dev/dotfiles log --oneline -1
```

### The repo-only paths

`REPO_ONLY` in `scripts/home_spec.py` lists the paths that never belong in `$HOME`: `.adr-dir`, `.gitattributes`, `.github`, `.gitignore`, `LICENSE.md`, `PLAN.md`, `README.md`, `build.gradle.kts`, `crates`, `docs`, `gradle`, `gradle.properties`, `gradlew`, `hk.pkl`, `justfile`, `pyproject.toml`, `renovate.json`, `tests`.

They were tracked in `$HOME` and are now only in `~/dev/dotfiles`. Remove the stale copies from `$HOME`.

First check that none of them holds untracked content — this is the one irreversible risk in the migration, because the tracked copies are already safely in `~/dev/dotfiles` but anything untracked under those paths would not be:

```bash
git -C ~/dev/dotfiles status --porcelain --ignored -- docs tests crates .github gradle dev
```

Anything reported as untracked (`??`) must be moved into `~/dev/dotfiles` by hand first. On this machine `crates` and `dev` carry ignored build/artifact directories (`crates`: 2 ignored entries, `dev`: 93) — `dev/` is a container for other checkouts, not dotfiles content, so leave `~/dev` alone except for the repo itself.

Then remove the stale copies:

```bash
rm -rf ~/docs ~/tests ~/crates ~/gradle ~/build.gradle.kts ~/gradle.properties ~/gradlew \
       ~/hk.pkl ~/justfile ~/pyproject.toml ~/renovate.json ~/README.md ~/PLAN.md \
       ~/LICENSE.md ~/.adr-dir ~/.gitattributes ~/.gitignore ~/.github
```

Do **not** delete `~/.git` from `~/dev/dotfiles`; it is the repository.

### Worktrees

The linked worktrees under `~/.worktrees/dotfiles/` still point at the old `~/.git`. Relocate them:

```bash
mkdir -p ~/.worktrees/dev-dotfiles
git -C ~/dev/dotfiles worktree repair                       # fixes stale gitdir pointers
git -C ~/dev/dotfiles worktree move ~/.worktrees/dotfiles/main ~/.worktrees/dev-dotfiles/main
git -C ~/dev/dotfiles worktree move ~/.worktrees/dotfiles/home-overlay ~/.worktrees/dev-dotfiles/home-overlay
git -C ~/dev/dotfiles worktree list
```

`git worktree repair` is required first, and it must run **before** the `worktree move` calls. After `.git` moves, each worktree's `.git` file still points at the old `~/.git/worktrees/<name>` path, which no longer exists; `repair` rewrites those pointers, and `worktree move` then relocates the worktree directory and updates the pointer again. Both steps were verified in a sandbox: without `repair`, every worktree errors with `fatal: gitfile does not point to a valid repository`.

Stale directories `~/.worktrees/dotfiles/ben/` and `~/.worktrees/dotfiles/phatblat/` are not registered worktrees; remove them once you have confirmed nothing is in them.

## Phase 2 — Seed and deploy the overlay

`~/.config/mise/conf.d/dotfiles.toml` does not exist yet, and it is itself one of the deployed files. Bootstrap it by hand:

```bash
mkdir -p ~/.config/mise/conf.d
cp ~/dev/dotfiles/.config/mise/conf.d/dotfiles.toml ~/.config/mise/conf.d/dotfiles.toml
```

Then deploy. The first `apply` will refuse to overwrite the real files that are still in `$HOME` — that refusal is the safety mechanism, and it means the transition is explicit rather than destructive:

```bash
mise --cd "$HOME" dot apply --yes --dry-run    # read the plan first
mise --cd "$HOME" dot apply --yes --force       # force the transition
```

`--force` is safe here specifically because the sources are the same tracked content that the real files were created from. Two caveats, both verified in a sandbox:

- `--force` replaces an existing **directory** with a symlink, and it **deletes the directory's contents** to do it. On this machine that does not bite: an audit of all 2304 spec entries found **zero** targets that are real directories (2210 are already regular files or symlinks, 94 are absent), because every directory in the spec is a container whose individual files are listed separately. If that audit ever reports a real directory, move its contents aside before applying.
- `--force` does **not** overwrite `copy`-mode targets. Those entries (`.claude.json`, `.oc/config.json`, `.gemini/config/config.json`, `.gemini/antigravity-cli/settings.json`, `Library/Application Support/Claude/claude_desktop_config.json`) are app-owned: the live file always wins, and the repo copy is refreshed by `just home-capture`. The live file is left alone, so nothing is lost, but the repo copy may be stale — capture it.

After the first forced apply:

```bash
just home-capture      # copy app-owned live files back into the repo
just home-status       # shows any remaining drift
```

From here on, `just home-apply` is the canonical way to re-deploy (it runs `home_spec.py links` first to recreate the dangling-class links, then `mise dot apply`). The `dotfiles-apply` git hook installed in Phase 3 does the same thing automatically after every checkout, merge, commit, or history rewrite in the primary checkout.

### Files that cannot be deployed automatically

- `~/.agents/skills/{authoring-skills,conventional-docs,recording-changes,semantic-versioning,setup-phatblat-skills}` — the spec deploys these as direct relative links to `~/dev/agents/...`, but those source checkouts do not exist on this machine yet. Clone them first (see below), then re-apply.
- `bin/vi`, `bin/vim`, `~/.config/iterm2/AppSupport` — these point at absolute paths that do not exist here (`/opt/homebrew/bin/nvim`, `~/Library/Application Support/iTerm2`). `mise` refuses to link a non-existent source. The repo's `scripts/home_spec.py` recreates them with the repo's own link text via `just home-apply` (which runs `home_spec.py links` first). Install `neovim` and iTerm2, or accept the links as dangling.
- `~/Library/Application Support/nushell/autoload` — a tracked relative symlink (`../../../.config/nushell/autoload`) that keeps working after the move because the link is deployed into `$HOME`, not into the repo.

### The out-of-repo skill sources

```bash
git clone https://github.com/phatblat/skills.git ~/dev/agents/skills
git clone https://github.com/phatblat/conventional-docs.git ~/dev/agents/conventional-docs
```

The layout must be `~/dev/agents/skills/skills/<skill>` and `~/dev/agents/conventional-docs/skills/conventional-docs`; `phatblat/skills` has its skills under `skills/`, so cloning into `~/dev/agents/skills` gives `~/dev/agents/skills/skills/<name>` as the spec expects.

Re-run `mise --cd "$HOME" dot apply --yes` afterwards to create those five links.

## Phase 3 — Reinstall the git hooks and filters

The hooks and clean filters live in the repo's local git config, which moved with `.git`. Two things need attention:

- `core.hooksPath` is the relative path `.config/git/hooks`, resolved against the **work tree root**. After the move that is `~/dev/dotfiles/.config/git/hooks`, which does not exist (the tracked `.config/git/` holds `attributes` and `config`, not hooks). The directory does not have to exist for the config-based hooks to fire — git 2.54+ config hooks (`hook.<name>.command`) run regardless of `core.hooksPath`, and that is how `hk` installs here. But `core.hooksPath` does override the default `.git/hooks` directory, so the five script hooks that live there today (`pre-commit`, `pre-push`, `post-checkout`, `post-commit`, `post-merge`) are already being bypassed on this machine. Reinstall so the intended hooks are in place:

  ```bash
  cd ~/dev/dotfiles
  just git-hooks
  ```

  This installs `hk`'s pre-commit hook and the new `dotfiles-apply` hook (`post-checkout`, `post-merge`, `post-commit`, `post-rewrite`) that re-runs `mise dot apply` in the primary checkout after every write. The `dotfiles-apply` hook is what keeps `$HOME` in sync after a commit — without it, the links only update when you run `just home-apply` by hand.

  Note `just git-hooks` writes `hook.dotfiles-apply.command` as an absolute path to `$primary/scripts/home-apply-hook`, where `$primary` is derived from `git rev-parse --git-common-dir`. That derivation follows the relocation automatically, so the hook points at `~/dev/dotfiles/scripts/home-apply-hook` once you run the recipe from the new location.

- The clean filters are configured with absolute paths pointing at `$HOME` (`filter.codex-config.clean=/Users/<you>/scripts/mask-codex-state.sh`). Those `$HOME` paths become symlinks into the repo after Phase 2, so they still resolve — but reinstall them anyway so they point at the repo copy:

  ```bash
  just git-filters
  ```

  Without this, staging `.codex/config.toml` or `.claude.json` commits unmasked content (a live API key in `.oc/config.json`, Anthropic-managed state in `.claude.json`).

  The codex hook-trust cache lives outside the repo at `~/.local/state/codex-hook-trust.tsv` and survives the move untouched.

## Phase 4 — Restore the `$HOME`-only paths

`.config/wt/overlay/dev-dotfiles` lists the paths that stay in `$HOME` and are linked into the primary checkout so worktrees can see the real tools and credentials:

```
.env
.local/bin/mise
.local/share/mise
.ssh
.netrc
.config/gh/hosts.yml
```

`just home-overlay-links` creates those links **in the primary checkout** (`~/dev/dotfiles/<entry>` → `$HOME/<entry>`), so the checkout sees the live tools and credentials:

```bash
cd ~/dev/dotfiles
just home-overlay-links
```

Note `.netrc` does not exist on this machine; the recipe prints `skip: ~/.netrc missing` and continues. `.env` is a real file and is not tracked (it is gitignored), so it must be linked into the checkout rather than deployed into `$HOME` — `home-overlay-links` does that.

These overlay entries are deliberately *not* in the `mise dot` spec: they are `$HOME`-only paths, so deploying them from the checkout would make the checkout depend on itself.

### `.cursor/skills` must exist in the checkout

The harness probe resolves paths against the **checkout root**, not `$HOME`. `.cursor/skills` is gitignored (Cursor's own managed block in `.cursor/.gitignore` re-ignores it) and is materialised by agentlink, not tracked — so it is absent from a fresh checkout, and `just harness-probe` reports `cursor skills.shared` as failing.

Run `just agentlink-apply` once after the move, from the checkout:

```bash
cd ~/dev/dotfiles
just agentlink-apply
```

It creates `.cursor/skills` as a symlink to `.agents/skills`. Without it the probe fails on every run.

### Approve the checkout's `.envrc`

direnv records approvals per `.envrc` path, so the checkout's copy needs its own approval. Otherwise every shell in the checkout prints `direnv: error ... .envrc is blocked`:

```bash
direnv allow ~/dev/dotfiles/.envrc
```

Also install the launch agents, which now read from the checkout rather than from `$HOME`:

```bash
just install-launchagents
just install-launchdaemons
```

The plists themselves changed `cd "$HOME"` to `cd "$HOME/dev/dotfiles"`. They are copied (not symlinked) into `~/Library/LaunchAgents`, because launchd ignores links.

## Phase 5 — Verify

```bash
cd ~/dev/dotfiles
just home-status        # every target should be a symlink into the checkout
just check              # lint, typecheck, harness parity, home-spec-check, tests
just doctor             # mise doctor, brew doctor, home-status, claude doctor
```

`just test` now remaps `HOME` to the checkout itself, so it runs correctly from any worktree.

Spot-check that the deployment actually took effect:

```bash
ls -l ~/.bashrc ~/.config/nushell/config.nu ~/justfile 2>&1   # symlinks into ~/dev/dotfiles
ls ~/justfile                                                # should not exist
git -C ~/dev/dotfiles status --porcelain                     # empty
wt list                                                      # worktrees under ~/.worktrees/dev-dotfiles
```

The `wt` path key changes with the repo location: `path_key` is the repo root with the `$HOME` prefix stripped and `/` replaced by `-`, so `~/dev/dotfiles` becomes `dev-dotfiles`. That is why the overlay manifest was renamed from `dotfiles` to `dev-dotfiles` and why worktrees move to `~/.worktrees/dev-dotfiles/`.

## What `just home-deploy` / `just home-live` do after the move

`just home-deploy <ref>` pins `$HOME` to a commit by detaching the primary checkout at `~/dev/dotfiles`; the post-checkout hook then re-applies the links so `$HOME` follows that ref. `just home-live` switches back to the branch it left. Both refuse refs that lack `.config/mise/conf.d/dotfiles.toml` or `scripts/home-apply-hook`, because checking out such a ref would orphan every link in `$HOME`.

## Rollback

Before starting, record the state so it can be reversed:

```bash
git -C ~/dev/dotfiles rev-parse HEAD > /tmp/dotfiles-pre-migration-head
cp ~/dev/dotfiles/.git/config /tmp/dotfiles-pre-migration-gitconfig
```

To roll back, move `~/dev/dotfiles/.git` back to `~/.git`, move the tracked files back to `$HOME`, restore the git config, move the worktrees back under `~/.worktrees/dotfiles/`, and remove `~/.config/mise/conf.d/dotfiles.toml` plus the deployed symlinks. Because the deployed files are symlinks into the repo, the reverse operation is mechanical — but only the tracked content is recoverable, which is why Phase 1 insists that no untracked file lives under a repo-only path.
